# 브랜치 전략

1인 개발 + AI 에이전트 기반 QA를 전제로 한 간소한 전략입니다.

## 브랜치 구조

```
prod ─────────────────────────────────
  ▲                    ▲
  │ (승격 PR)           │ (긴급 배포 후 백머지)
  │                     │
 dev ◄──────────────┐  hotfix/{이슈번호}-{설명}
  ▲                  │  (prod에서 직접 분기)
  │ (PR)             │
  └── feat|fix|refactor|docs|chore/{이슈번호}-{설명}
```

- `prod` : 운영 배포 브랜치
- `dev` : 기본 작업 브랜치, 모든 기능 브랜치의 기점
- `hotfix/{이슈번호}-{설명}` : `prod`에서 발생한 장애를 즉시 고치기 위해 `prod`에서 직접 분기 → `prod`에 먼저 머지해 배포 → 이후 `dev`로 백머지

`stg`(QA 브랜치)는 두지 않습니다. QA를 별도 인력이 아닌 본인/QA 에이전트가 수행하므로 `dev`의 프리뷰 배포에서 검증 후 `prod`로 바로 승격합니다. 여러 기능을 모아 배치 릴리즈해야 하는 필요가 생기면 그때 `stg` 도입이나 feature flag를 재검토합니다.

## 브랜치 접두사

이슈 하나 = 브랜치 하나 = PR 하나 원칙으로, 이슈 생성 비용이 낮다는 점을 활용해 스코프를 작게 유지합니다.

| 접두사 | 의미 |
|---|---|
| `feat/{이슈번호}-{설명}` | 기능 추가·변경 (UI/CSS 변경처럼 사용자 경험에 영향을 주는 변경 포함) |
| `fix/{이슈번호}-{설명}` | 버그 수정 |
| `refactor/{이슈번호}-{설명}` | 동작 변화 없는 구조 개선 |
| `docs/{이슈번호}-{설명}` | 문서 변경 |
| `chore/{이슈번호}-{설명}` | 그 외 전부 (포매팅, prettier/eslint, 설정, 의존성 등 결과물에 영향 없는 변경) |

`style` 접두사는 별도로 두지 않고 `chore`에 흡수합니다.

## 릴리즈 흐름

1. `dev`에서 위 접두사로 브랜치 생성 → 작업 → PR → `dev` 머지
2. `dev` 프리뷰 배포에서 QA(본인 또는 QA 에이전트) 수행
3. 검증 통과 시 `dev → prod` 승격 PR
4. `prod` 장애 발생 시 `hotfix/{이슈번호}-{설명}` 분기 → `prod` 머지·배포 → `dev`로 백머지 PR

## 커밋 전략

- 형식(Conventional Commits, 브랜치 접두사와 동일한 5개 타입): `{type}: {설명} (#이슈번호)` + 필요시 본문에 상세 변경점 나열
  ```
  feat: 카테고리 필터 추가 (#12)

  - 필터 드롭다운 컴포넌트 추가
  - API 쿼리에 category 파라미터 반영
  ```
- 브랜치 내 커밋(`feat/...` 등)은 자유롭게 WIP으로 쌓아도 됨 — 어차피 머지 시 squash됨
- **머지 전략**
  - `feat|fix|refactor|docs|chore/* → dev` : **Squash and merge**. PR 머지 시점에 커밋 메시지를 위 형식(제목 + 상세 변경점)으로 정리
  - `dev → prod`, `hotfix/* → prod` : **Merge commit**. 이미 squash된 이력을 그대로 보존

**Why:** 1인 개발이라 여러 기여자 간 커밋 단위 blame을 추적할 필요가 없고, `dev`의 각 커밋이 "완결된 PR 단위"로 남아야 롤백(`git revert` 한 번)과 원인 파악(bisect 시 중간에 깨진 WIP 상태를 밟지 않음)이 쉬워짐. 세부 커밋 히스토리가 필요하면 squash 전에도 GitHub PR 페이지에서 원본 커밋을 확인 가능. 팀 프로젝트로 바뀌면 blame 추적을 위해 merge commit이나 rebase and merge로 전환을 재검토.

## 이슈 / PR 템플릿

- 이슈: `.github/ISSUE_TEMPLATE/issue_template.md`
- PR: `.github/PULL_REQUEST_TEMPLATE.md`

이슈와 PR 모두 동일한 유형(`feat`/`fix`/`refactor`/`docs`/`chore`) 체크박스를 사용하며, 이슈 번호 → 브랜치 접두사 → PR 유형이 항상 일치해야 합니다. PR은 반드시 관련 이슈를 `Closes #`로 연결합니다.

## AI에게 작업을 맡길 때

- 새 작업은 항상 이슈 생성 → `dev`에서 이슈에 대응하는 접두사로 브랜치 생성 → 작업 → PR(템플릿 사용, 이슈 연결) 순서를 따릅니다.
- 이슈 하나, 브랜치 하나, PR 하나가 1:1로 매핑되도록 스코프를 작게 유지합니다.
- `stg` 브랜치는 사용하지 않습니다. QA는 `dev` 프리뷰 배포에서 수행합니다.
- `prod` 장애 대응 시에만 `hotfix/` 브랜치를 예외적으로 `prod`에서 직접 분기합니다.
